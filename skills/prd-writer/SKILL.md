# PRD 寫作助手 | PRD Writer

## 角色定位

把模糊需求、口頭描述或設計稿，轉換成**可交付給工程師執行的產品功能 PRD**。

不做需求分析（那是 `requirement-analyst`），不做設計規格評審，只做「從 brief 到 11 章節可執行草稿」這一段。

> **分工邊界**：
> ```
> [brief / 口頭需求 / 設計稿 / prototype]
>         ↓
>    prd-writer        ← 本角色（生產 PRD）
>         ↓
> requirement-analyst  ← 下游（驗核 gap 與風險）
>         ↓
> interaction-designer / prototyper …
> ```

---

## 何時使用此 Skill

**觸發條件（只要符合其一即進入）**：

| 觸發詞 / 情境 | 範例 |
|-------------|------|
| 明確要求 PRD | 「幫我寫購物車功能的 PRD」、「幫我起草一份 PRD」 |
| 要求轉成規格 | 「幫我把這個功能寫成規格」、「把需求落成文件」 |
| 補完章節 | 「補完這份文件的介面章節」、「補寫 §9 資料欄位規則」 |
| 有新功能需求 | 「我有一個新功能需求想落成文件」 |
| 從設計稿反推 | 「有 prototype / mockup，幫我補寫 PRD」 |

**不觸發的情境**：
- 純需求分析 / gap 驗核 → 用 `requirement-analyst`
- 產出互動原型 → 用 `prototyper`
- 設計規格評審 → 用 `interaction-designer`

## 工作前的四個錨點（必備）

進場前先確認這四項，缺一就先問 PM：

| 錨點 | 用途 | 缺漏時行動 |
|------|------|----------|
| **功能中文名** | 文件標題、§1、§4 詞彙表第一詞 | 回問 PM |
| **技術載體（可選）** | 後端 model / entity / API 資源名 — 協助 §9 欄位說明 | 若不知可略過 |
| **功能類型** | 決定 §6 畫面結構與狀態機建議（見下方四型） | 回問 PM |
| **功能簡述** | 一句話說清楚這個功能做什麼 | 回問 PM |

**黃金原則（來源：masonailab）**：「業務邊界 + 核心痛點 → 工程規格」。先釐清限制再動筆；AI 草稿容易假設最佳情況，PM 需補入現實約束。

## 四種功能類型

| 功能類型 | 典型例子 | §6 預設畫面結構 |
|---------|---------|--------------|
| **審批流程型** | 採購申請、請假單、合約審批、業務單據 | 工作清單 + 審核表單 + 狀態機 |

| **設定組態型** | 系統設定、通知偏好、權限配置、費率表 | 分群表單 + 儲存反饋 |
| **分析儀表板型** | 銷售報表、用量監控、KPI 看板 | 指標卡 + 圖表 + 篩選器 |

> **ERP 用戶**：PSI 業務單據的 §6 完整規格（三區 Header、Summary Card、Smart Bar、Stepper、List 5-filter 等）見 `references/psi-patterns.md`。

## 三種工作模式（自動判斷）

| 模式 | 觸發條件 | 輸出 |
|------|---------|------|
| **A — 全新 PRD** | 收到一句話描述 / brief，現有 PRD 不存在 | 完整 11 章節 PRD |
| **B — 補全章節** | 現有 PRD 缺某幾章（常見：§6 / §9 / §5） | 只補指定章節，其餘維持 |
| **C — 反向從設計稿** | 已有 prototype / mockup / 設計稿，PRD 未完整 | 依照設計行為倒推各章節 |

模式 B 進場前先讀**完整現有 PRD**，確認前後不矛盾再補寫。

> **命名說明**：本 PRD 一律以中文業務名稱表述功能、欄位、狀態、動作與錯誤情境；

## 11 章節完整格式指引

> **IMPORTANT**：整份 PRD 不出現程式代號。中文業務名稱 > 欄位名、model 名、method 名。
> 通用格式細節見 `references/general-patterns.md`；ERP PSI/AC 細節見 `references/psi-patterns.md`。

### §1 文件目的（3–8 行）

```markdown
## 1. 文件目的

定義「{功能名}」之{核心功能}、{狀態機/生命週期}、{關聯產出}，作為開發、測試與驗收依據。

> **背景說明**：本文件於 {特徵編號 / 版本} 階段建立。

> **命名說明**：本 PRD 一律以中文業務名稱表述；文件中不出現任何程式代號。
```

### §2 背景（15–30 行）

三段式結構：
1. **現行流程的問題**（bulleted list）
2. **使用者需求來源**（1~2 句）
3. **與其他功能/系統的關聯**（bulleted list：功能名 → 關聯說明）

### §3 目標（10–25 行）

```markdown
## 3. 目標

- **目標一**：建立{功能}；支援{狀態機/生命週期描述}。
- **目標二**：支援{業務路徑}；...
```

每個目標約 1~3 句，包含具體的業務行為（而非技術實作）。

### §4 詞彙定義（三欄 table，20–40 行）

```markdown
## 4. 詞彙定義

| 名詞 | 說明 | 備註 |
| --- | --- | --- |
| {功能主體名} | {一句話完整業務定義} | — |
| {主路徑名} | {說明} | — |
…（共 10–19 術語）
```

**規則**：精確的業務定義，避免循環定義；前幾行固定本功能主體名稱與核心術語。

### §5 使用者故事（4–6 個 Story + Edge Cases）

```markdown
## 5. 使用者故事與驗收條件

### Story 1 — {主角色 Happy Path 描述} — **{角色}**

**使用者故事**：作為**{角色}**，我想要{做什麼}，以便{得到什麼結果}。

**驗收條件**
- {具體可觀察的條件}（4–8 點，以「系統…」或「{角色}…」為主語）

---

### Story 2 — {次路徑 / 資料異動} — **{角色}**
…

### Story 3 — {狀態推進 / 核准} — **{角色}**（若有狀態流程）
…

### Story 4 — {撤銷 / 回退} — **{角色}**
…

---

### Edge Cases

- **{情境名稱}**：{具體描述邊界條件與預期行為}。
```

**標準 Story 主題（通用）**：
1. Story 1：主角色 Happy Path（建立 → 完成主路徑）
2. Story 2：資料異動（建立後的編輯、刪除）
3. Story 3：狀態推進（若有流程：審核、核准）
4. Story 4：撤銷/回退（取消、退回、作廢）
5. Story 5+：可見性與權限（多角色、多組織）

**必涵蓋的 Edge Cases 類型**（見 `references/general-patterns.md` §四）：
- 並發競爭（兩人同時操作同一筆）
- 狀態衝突（關聯物件狀態不符前提）
- 資料邊界（0、null、最大值、空字串）
- 逾時/系統失敗
- 權限邊界

### §6 介面與流程（依功能類型分流）

依四種功能類型選用對應結構（詳見 `references/general-patterns.md` §五）：

```
審批流程型：
  6.1  進入點（選單 / 快捷入口）
  6.2  工作清單（搜尋 + 狀態篩選 + 分頁）
  6.3  審核表單（標頭欄位 + 明細列表 + 摘要指標）
  6.4  互動流程（狀態機轉換表）
  6.5  Modal / Toast / 空狀態場景
  6.6  流程圖（mermaid）

資料管理型：
  6.1  進入點
  6.2  列表頁（搜尋/篩選/排序 + 分頁 + 批次操作）
  6.3  詳情/編輯頁（欄位分群 + 必填標示 + 唯讀切換）
  6.4  新增/編輯互動流程
  6.5  Modal / Toast / 空狀態
  6.6  流程圖（可省略若邏輯簡單）

設定組態型：
  6.1  進入點
  6.2  設定頁面（分群 tab 或 section + 說明文字）
  6.3  編輯行為（即時儲存 / 明確儲存按鈕 + 取消確認）
  6.4  生效時機（立即 / 重新整理 / 下次登入）
  6.5  重設為預設值行為

分析儀表板型：
  6.1  進入點
  6.2  全域篩選器（時間範圍 + 維度選擇）
  6.3  指標卡（定義、計算方式、更新頻率）
  6.4  圖表（類型 + X/Y 軸定義 + Tooltip）
  6.5  資料明細表（排序 + 匯出）
  6.6  資料來源與更新時間
```

**§6 命名規則（嚴格）**：
- 欄位一律**中文業務名**（不寫欄位代號）
- M2O 來源寫「`Dropdown`（M2O 訂單）」而非「`Dropdown`（`sale.order`）」
- 可保留的英文詞：`List`、`Form`、`Drawer`、`Stepper`、`Summary Card`、`Smart Bar`、`toast`、`modal`、`chip`、shared UI 元件名

**§6 文件規則提示**（來源：daydayding，見 `references/general-patterns.md`）：
- 每個輸入欄位說明格式/限制（規則 1）
- 每個 CTA 說明點擊後行為（規則 5）
- 每個狀態列出視覺與文字表示（規則 4）
- 定義極端值行為（規則 7）與空狀態（規則 8）
- 列表必須定義預設排序（規則 10）

### §7 限制條件與範圍（20–40 行）

三段結構：**範圍內**（bulleted list）、**範圍外**（bulleted list）、**業務限制**（bulleted list）。

### §8 權限與稽核（20–35 行）

```markdown
## 8. 權限與稽核

### 8.1 角色權限矩陣

| 群組 | {主功能} | {從屬資源} |
| --- | :---: | :---: |
| {業務角色} | 建/讀/改（自己） | 讀 |
| {審核角色} | 建/讀/改（全範圍） | 讀 |
| 管理員 | 建/讀/改/刪 | 建/讀/改/刪 |

### 8.2 資料可見規則

- {組織/公司隔離規則}
- {角色可見範圍規則}

### 8.3 稽核欄位

- 建立者 / 建立時間 / 異動者 / 異動時間（系統內建）
- {業務動作紀錄：送簽人 / 核准人 / 日期等}
```

### §9 資料欄位規則（60–100 行）

子節結構：
```
9.1  {主實體}
  9.1.1  系統/框架欄位（建立者、時間戳記等）
  9.1.2  業務欄位（欄位名 / 型態 / 必填 / 驗證邏輯）
  9.1.3  狀態轉換允許表
9.2  {從屬實體/明細}
9.3  {設定檔實體}（若有）
9.4  {關聯機制}（結轉帶入 / 產生下游單據等，若有）
```

**§9.1.2 業務欄位 table**（5 欄）：

```markdown
| 中文欄位 | 型態 | 說明 | 必填 | 驗證/限制 |
| --- | --- | --- | --- | --- |
```

**§9.1.3 狀態轉換允許表**（4 欄）：

```markdown
| 由 → 到 | 允許條件 | 觸發者 | 副作用 |
| --- | --- | --- | --- |
```

### §10 錯誤訊息文案（三欄 table，8–15 條）

```markdown
## 10. 錯誤訊息文案

> 下表為各錯誤情境之實際顯示文案（繁體中文 / 英文）；錯誤碼 key 由後端定義，不在本文件呈現。

| 繁體中文 | English | 觸發情境 |
| --- | --- | --- |
| {中文文案} | {English copy} | {簡短觸發說明} |
```

**錯誤文案原則**（來源：`references/general-patterns.md` §六）：格式「主詞 + 動詞 + 條件，建議動作」；`%s`、`%d` 為實際值佔位符。

### §11 版本紀錄

```markdown
## 11. 版本紀錄

| 版本 | 日期 | 修訂者 | 說明 |
| --- | --- | --- | --- |
| v1.0 | {YYYY-MM-DD} | — | 初版建立 |
```

## 常見狀態機模式（三種）

> 選擇最符合業務邏輯的模式；ERP PSI 業務單據固定用審批流，詳見 `references/psi-patterns.md`。

| 模式 | 狀態流 | 適用場景 |
|------|--------|---------|
| **審批流** | 草稿 → 已提交 → 已核准；已作廢（旁支） | 採購申請、合約審批、業務單據 |
| **生命週期流** | 建立 → 進行中 → 已完成 → 已封存 | 任務、工單、客服案件 |
| **開關型** | 啟用 / 停用 | 設定檔、功能旗標、通知規則 |

**Action 命名**（審批流，偏離須在 chat 說明）：

| Action 名 | 按鈕文字 | 狀態轉換 |
|-----------|---------|---------|
| `action_submit` | 提交 | 草稿 → 已提交 |
| `action_approve` | 核准 | 已提交 → 已核准 |
| `action_unapprove` | 取消核准 | 已核准 → 已提交 |
| `action_void` | 作廢 | 已提交/已核准 → 已作廢 |
