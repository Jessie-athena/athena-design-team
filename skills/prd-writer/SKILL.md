# PRD 寫作助手 | PRD Writer

## 角色定位

把模糊需求、口頭描述或設計稿，轉換成**可交付給工程師執行的 Athena ERP 模組 PRD**。

不做需求分析（那是 `requirement-analyst`），不做設計規格評審，只做「從 brief 到 11 章節可執行草稿」這一段。

> **分工邊界**：
> ```
> [brief / 口頭需求 / prototype]
>         ↓
>    prd-writer        ← 本角色（生產 PRD）
>         ↓
> requirement-analyst  ← 下游（驗核 gap 與風險）
>         ↓
> interaction-designer / prototyper …
> ```

---

## 何時使用此 Skill

**觸發條件（只要符合其一即進入）**：

| 觸發詞 / 情境 | 範例 |
|-------------|------|
| 明確要求 PRD | 「幫我寫銷貨退回的 PRD」、「幫我起草一份 PRD」 |
| 要求轉成規格 | 「幫我把這個功能寫成規格」、「把需求落成文件」 |
| 補完章節 | 「補完這份文件的介面章節」、「補寫 §9 資料欄位規則」 |
| 有新模組需求 | 「我有一個新模組需求想落成文件」 |
| 從 prototype 反推 | 「有 prototype，幫我補寫 PRD」 |

**不觸發的情境**：
- 純需求分析 / gap 驗核 → 用 `requirement-analyst`
- 產出互動原型 → 用 `prototyper`
- 設計規格評審 → 用 `interaction-designer`

| 模式 | 觸發條件 | 輸出 |
|------|---------|------|
| **A — 全新 PRD** | 收到一句話描述 / brief，現有 PRD 不存在 | 完整 11 章節 PRD |
| **B — 補全章節** | 現有 PRD 缺某幾章（常見：§6 / §9 / §5） | 只補指定章節，其餘維持 |

## 11 章節完整格式指引

> **IMPORTANT**：整份 PRD 不出現程式代號。中文業務名稱 > 欄位名、model 名、method 名、CSS class、設定參數鍵。
> 完整格式細節見 `references/psi-patterns.md`。

### §1 文件目的（3–8 行）

```markdown
## 1. 文件目的

定義「{模組名}」之{核心功能}、{狀態機}、{關聯產出}，作為{模組}開發、測試與驗收依據。

> **背景說明**：本主檔於 {特徵編號} 階段（{日期}）建立。

> **命名說明**：本 PRD 一律以中文業務名稱表述功能、欄位、狀態、動作與錯誤情境；**文件中不出現任何程式代號**。
```

### §2 背景（15–30 行）

三段式結構：
1. **現行流程的問題**（bulleted list）
2. **使用者需求來源**（1~2 句）
3. **與其他模組的關聯**（bulleted list：模組名 → 關聯說明）

### §3 目標（10–25 行）

```markdown
## 3. 目標

- **目標一**：建立{模型名}，含訊息追蹤（chatter）；支援{狀態機描述}。
- **目標二**：支援{業務路徑}；...
- **目標三**：...
```

每個目標約 1~3 句話，包含具體的技術行為。

### §4 詞彙定義（三欄 table，20–40 行）

```markdown
## 4. 詞彙定義

| 名詞 | 說明 | 備註 |
| --- | --- | --- |
| {模組單據名} | {一句話完整業務定義} | — |
| {主路徑名} | {說明} | — |
| {次路徑名} | {說明} | — |
| {核心明細名} | {說明} | — |
…（共 12–19 術語）
| {傳票相關術語} | {說明} | 末幾行為傳票術語 |
```

**規則**：
- 約 12–19 個術語（業務單據通常 15+）
- 說明 = 精確的業務定義，避免循環定義
- 前幾行固定：本單名稱、主路徑、次路徑、核心明細名、關鍵業務術語
- 末幾行固定：傳票相關術語、反沖術語（若有傳票）

### §5 使用者故事（5 個 Story + 8–12 條 Edge Cases）

```markdown
## 5. 使用者故事與驗收條件

### Story 1 — {主角色 Happy Path 描述} — **{角色}**

**使用者故事**：作為**{角色}**，我想要{做什麼}，以便{得到什麼結果}。

**驗收條件**

- {具體可測試的條件}（4–8 點，以「系統…」或「{角色}…」為主語）

---

### Story 2 — {次路徑（如：結轉）} — **{角色}**
…

### Story 3 — {核准後動作（如：產傳票）} — **{角色}**
…

### Story 4 — {取消核准／解核} — **{角色}**
…

### Story 5 — {公司隔離與可見性} — **{角色}**
…

---

### Edge Cases

- **{情境名稱}**：{具體描述邊界條件與預期行為}。
```

**標準 5 個 Story 主題（業務單據）**：
1. Story 1：主角色 Happy Path（建單 → 送簽 → 核准 + 核准產出）
2. Story 2：次路徑（若有結轉路徑：從來源單結轉）
3. Story 3：核准後動作（產傳票或下游連動）
4. Story 4：取消核准／解核（反向操作）
5. Story 5：公司隔離與可見性（多公司 + 角色權限）

**必涵蓋的 Edge Cases 類型**（8–12 條）：
1. 並發競爭（兩人幾乎同時操作同一筆）
2. 作廢已產傳票（須先手動反沖）
3. 金額/數量為 0 的行（暫存 vs 送簽/核准時移除）
4. 跨公司驗證（退回單/採購單必須同公司）
5. NULL / 未設定主檔（客戶/供應商未設科目的三層 fallback）
6. 狀態不一致（已作廢關聯單欲繼續操作）
7. 限制 flag 控制（boolean 旗標為 false 時整組停用）

### §6 介面與流程（業務單據標準子節，300–500 行）

```
6.1  選單與進入點
6.2  List View（列表）
  6.2.1  工具列
  6.2.2  搜尋區
  6.2.3  欄位順序
  6.2.4  列表行為
  6.2.5  分頁器
6.3  Form View（表單）
  6.3.1  表單結構總覽
  6.3.2  Summary Card
  6.3.3  表頭分群欄位
  6.3.4  明細 Section（含 Drawer 規格）
  6.3.5  表單底部操作列（Footer）
  6.3.6  Smart Bar（智慧列）
6.4  互動流程（狀態機轉換文字說明 + 表格）
6.5  Modal / Toast 場景
6.6  流程圖（mermaid 圖）
```

**§6 命名規則（嚴格）**：
- 欄位一律**中文業務名**（不寫欄位代號如 `sale_id`、`partner_id`）
- M2O 來源寫「`Dropdown`（M2O 銷貨單）」而非「`Dropdown`（`psi.sale_order`）」
- 系統參數寫「系統參數『銷貨退回日記帳』」而非 `psi_sale_return_journal_id`
- 可保留的英文詞：`List`、`Form`、`Drawer`、`Stepper`、`Summary Card`、`Smart Bar`、`toast`、`modal`、`chip`、shared UI 元件名（`TextBox`、`Dropdown`、`DataGrid`、`DatePicker` 等）
- `action_submit`、`action_approve` 等 action 名**保留**（§6.4 互動流程可用）

**§6.2.1 工具列格式**（table）：

```markdown
| 狀態 | 左群 | 右群（固定） |
| --- | --- | --- |
| 未勾選 | 「新增{單}」（主要按鈕）＋「匯入」（外框） | 分群下拉 ＋「⚙ 設定」 |
| 已勾選 N 筆 | 「↓ 匯出選取項」＋「🗑 刪除所選草稿」（條件顯示）＋「已選取 N 筆 ×」標籤 | 同上 |
```

PSI 慣例：**無批次作廢**（草稿=物理刪除 unlink、已提交以上=作廢 voided）。

**§6.2.2 搜尋區格式**（table）：

```markdown
| 欄位（label） | 元件 | 響應式優先序 | 預設值 / 限制 |
| --- | --- | --- | --- |
| {單號} | `TextBox` | 最高 | 空；按 Enter 觸發查詢 |
| {對象} | `Dropdown`（M2O） | 高 | 空 |
| {經辦人} | `Dropdown`（M2O） | 中 | 空 |
| 日期區間 | `DatePicker`（Range） | 中 | 空 |
| 狀態 | `Dropdown` | 最高 | **第一選項固定「全部」（空值）** |
```

PSI 慣例：**5 個為基本集**（單號 / 對象 / 經辦人 / 日期區間 / 狀態），精簡不超過 6 個。
若模組有強關聯鍵（如採購扣補單有「來源採購單號」、銷貨退回有「來源銷貨單號」），可加第 6 個 filter；其他情況維持 5 個。

**§6.2.3 欄位順序格式**（table，9–11 欄）：

```markdown
| # | 欄位 | 元件 | 對齊 | 凍結 | 最小寬度 | 說明 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | ☐ 勾選 | `Checkbox` | 置中 | 凍結左 | — | 全選 |
| 2 | {主鍵單號} | `Link` | 靠左 | 凍結左 | 200px | 點擊進 Form |
| 3 | {對象名} | 純文字 | 靠左 | — | 180px | — |
…
| N | 操作 | `IconButton` | 置中 | 凍結右 | 56–96px | — |
```

PSI 慣例：金額僅留**一欄含稅總額**，tfoot 合計單欄帶標籤前綴（如 `採購合計: {Σ}`）。

**§6.3.2 Summary Card（PSI 業務單據標準）**：
- 左側：金額**等式橫向排列**「未稅金額 ＋ 稅額 ＝ 總金額」（總金額為主指標放大）
- 金額列右側：「已產生傳票號碼」chip（綠色，有關聯傳票時顯示）
- 右側：3 步 Stepper（草稿 / 已提交 / 已核准）；`voided` 整條換紅底 `voided-banner` pill

**§6.3.3 表頭三區模型（PSI）**：

```markdown
| # | 欄位 | 元件 | 必填 | 新增 | 已提交（有限編輯） | 凍結期（已核准起） | 說明 |
```

三區模型：
- **識別區（首）**：本單單號（第 1 格，唯讀，新增顯「/」） → 來源單號
- **決策區（中段）**：對象（供應商/客戶）→ 單據類型 → 經辦人 → 日期（**經辦人固定排在日期前**）
- **隔離區（末）**：帳簿（日記賬）→ 應付/應收科目 → **公司別**（唯讀帶入，壓末）→ 幣別

**§6.3.5 Footer 動作按鈕**（依狀態條件顯示）：
- 草稿：「提交」主要按鈕
- 已提交：「核准」主要按鈕
- 已核准：「取消核准」外框按鈕
- 更多操作下拉（全狀態）：「作廢」/「列印」/「複製為新單」

### §10 錯誤訊息文案（三欄 table，8–15 條）

```markdown
## 10. 錯誤訊息文案

> 下表為各錯誤情境之實際顯示文案（繁體中文 / 英文）；錯誤碼 key 由後端定義，不在本文件呈現。

| 繁體中文 | English | 觸發情境 |
| --- | --- | --- |
| {中文文案} | {English copy} | {簡短觸發說明} |
```

**錯誤文案格式參照**：

| 情境類型 | 繁體中文格式 | English 格式 |
|---------|------------|-------------|
| 必填缺值 | `{單據名} 有 {N} 條明細未設定{欄位名}，無法{動作}。` | `{Record} has {N} line(s) without {field}. Cannot {action}.` |
| 關聯不一致 | `{欄位A} 必須與{來源}一致。` | `{Field A} must match {source}.` |
| 跨公司 | `{A} 必須屬於本公司。` | `{A} must belong to the company.` |
| 狀態限制 | `{已...狀態} 之 {單據名} 不可 {動作}，請先 {前置動作}。` | `Cannot {action} {record} with {status}. Please {pre-action} first.` |
| 數量超限 | `第 %d 行 {欄位名} %s 超過 {上限名} %s（{計算說明}）。` | `Line %d {field} %s exceeds {limit} %s ({formula}).` |

原則：`%s`、`%d` 為實際值佔位符；約 8–15 條（核心驗證 + 關鍵限制）。

## 狀態機固定命名（業務單據）

| 狀態 key | 顯示名稱 | 備註 |
|----------|---------|------|
| `draft` | 草稿 | 可全編輯 |
| `submitted` | 已提交 | 有限編輯（特定欄位鎖定） |
| `approved` | 已核准 | 全唯讀；後端三層防禦 |
| `voided` | 已作廢 | 終態；軟刪除（停用） |

| Action key | 按鈕文字 | 狀態轉換 |
|-----------|---------|---------|
| `action_submit` | 提交 | 草稿 → 已提交，取號 |
| `action_approve` | 核准 | 已提交 → 已核准，觸發核准連動 |
| `action_unapprove` | 取消核准 | 已核准 → 已提交，逆向操作 |
| `action_void` | 作廢 | 已提交/已核准 → 已作廢 |

**偏離上述命名須在 chat 中明確說明理由。**

**取號時機兩種**：
- **送簽取號**：草稿為空（顯示「/」），送簽時系統取號。多數採購類單據。
- **草稿首存取號**：草稿首次儲存即配號，後續各動作維持原號。銷貨退回、部分銷貨類單據。

## Wizard-less 慣例（PSI）

**結轉帶入明細**（不做結轉精靈）：
- 表頭選定「原來源單」時 onchange 自動帶入可○量 > 0 的明細
- 帶入後數量欄預設 0，於 Drawer 逐筆輸入
- 儲存時自動移除數量 0 的行
- 驗證點：Drawer 即時 + 送簽 + 核准（三重驗證）

**產生傳票**（不做產傳票精靈）：
- Footer「建立傳票」直接按鈕
- primary confirm modal → 直接產生，無分錄預覽
- 日記帳/科目/日期/摘要系統自動取值
- 按科目分組產出多分錄

## 財務模組（AC）Header 欄位排序差異

> PSI 用三區模型；AC 改用**雙列模型**。

| 列 | 欄位 |
|----|------|
| 第一列（業務） | 單號 → 對象 → 主日期 → 次日期 → 產生方式 |
| 第二列（後台） | 公司別 → 部門 → 稅務公司 → 幣別 |

PSI 的公司別在末尾；AC 的公司別在第二列首位。寫混用模組時注意區分。
