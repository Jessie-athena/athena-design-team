# 通用 PRD 撰寫慣例

> 整合來源：daydayding.com/prd（10 條文件規則）與 masonailab.com/career/ai-pm-prd（AI PM 實踐）。
> ERP 領域細節（PSI 三區模型、狀態機、§6 ERP shell）→ 見 `psi-patterns.md`。

---

## 一、PRD 的目的與讀者

PRD 要讓三種讀者都能看懂並按圖施工：
- **工程師**：實作依據（欄位、驗證、狀態轉換、邊界條件）
- **設計師**：互動規格（流程、狀態、空狀態、錯誤）
- **QA**：驗收標準（AC、邊界情境、系統失敗情境）

寫法原則：「**業務邊界 + 核心痛點 → 工程規格**」。給出清楚的業務限制，而不是只描述理想路徑。AI 產生的草稿容易假設最佳情況（如「API 回應在 1 秒內」），需要 PM 補入現實約束。

## 二、10 條 PRD 文件規則

> 來源：daydayding.com/prd — 適用於所有 PRD 的 §6 / §9 / §10 章節。

### 規則 1 — 欄位規則
明確每個輸入欄位的格式、長度限制、允許字元與驗證邏輯。

```
欄位：電子郵件
格式：標準 email（包含 @ 與網域）
長度：最長 254 字元
驗證：格式錯誤時 → 顯示錯誤訊息（見 §10）
```

### 規則 2 — 錯誤狀態
為每個使用者操作定義失敗情境與對應文案；不只寫「成功路徑」。

文案原則：主語 + 動詞 + 原因，並提示解決方向。
範例：「電子郵件格式不正確，請重新輸入有效格式。」

### 規則 3 — 成功狀態
明確定義系統在操作成功後如何回饋：toast 通知、狀態更新、頁面跳轉或 modal 確認。

範例：儲存成功 → toast「已儲存」3 秒後消失；頁面留在編輯態。

### 規則 4 — 狀態指示
每個有多種狀態的物件，都需要列出全部狀態及其視覺/文字表示。

格式建議（table）：

| 狀態 | 顯示標籤 | 顏色/樣式 | 可執行動作 |
|------|---------|----------|---------|
| 草稿 | 草稿 | 灰色 | 編輯、提交 |
| 啟用 | 啟用中 | 綠色 | 停用 |

### 規則 5 — User Flow（使用者路徑）
標記主要 CTA 路徑與各畫面間的導向關係；每個 CTA 都要說明點擊後的行為。

用 mermaid 流程圖或文字步驟描述，至少涵蓋 Happy Path。

### 規則 6 — 邏輯流程圖
複雜條件分支（如：權限判斷、多步驟審批、系統自動處理）用流程圖呈現，不要只用文字描述。

推薦工具：mermaid `flowchart`（可直接貼入 PRD）。

### 規則 7 — 極端值
考慮資料量極端情況：超長文字（100 字標題）、超大數字（億元金額）、超多列表項（1000 筆）。

寫法：列出最大允許值，並說明超出時的行為（截斷/換行/錯誤）。

### 規則 8 — 空狀態
列表頁無資料時、搜尋無結果時、功能尚未設定時 — 每種空狀態都需要設計說明。

最少包含：icon 選擇、主訊息、副訊息（可選）、CTA（若適用）。

### 規則 9 — 資料來源
說明每個顯示欄位的資料來源（哪個 API / model / 計算邏輯）；特別標注非即時資料（快取/批次更新）。

### 規則 10 — 排序邏輯
動態產生的列表必須定義預設排序規則；說明使用者是否可手動改排序，以及排序後的持久性。

## 三、User Story + 驗收條件格式

> 來源：masonailab.com — AI PM 強調的 Story 撰寫規範。

### Story 格式

```markdown
### Story N — {描述} — **{角色}**

**使用者故事**：作為**{角色}**，我想要{做什麼}，以便{得到什麼結果}。

**驗收條件**
- {系統/使用者可觀察的具體行為}（4–8 點）
```

### 一份 PRD 標準 Story 數量

| 功能複雜度 | Story 建議數量 |
|---------|-------------|
| 單一功能（CRUD） | 3–4 個 |
| 有狀態流程（審批/生命週期） | 4–6 個 |
| 跨系統整合 | 5–7 個 |

### 五個常見 Story 主題（通用版）

1. **主路徑**：主角色從建立到完成的 Happy Path
2. **編輯/修改**：建立後的異動與版本控制
3. **審核/狀態推進**（若有流程）：推進狀態的角色與條件
4. **撤銷/回退**：逆向操作（取消、退回、作廢）
5. **查閱/搜尋**：不同角色的資料可見範圍與篩選

## 四、Edge Cases 標準清單

> 來源：masonailab.com — 強調「邊界條件比 Happy Path 更難寫、更重要」。

每份 PRD 的 §5 至少涵蓋以下 **6 類** Edge Cases（不一定每類都用，但逐一確認）：

| 類型 | 描述 | 範例 |
|------|------|------|
| **並發競爭** | 兩個使用者同時操作同一筆資料 | 同時核准同一申請單 |
| **狀態衝突** | 關聯物件狀態不符合操作前提 | 已停用的商品被加入訂單 |
| **資料邊界** | 極端值（0、null、最大值、空字串） | 數量為 0 的明細行 |
| **逾時/失敗** | 系統呼叫超時或外部服務失敗 | 付款 API 無回應 |
| **權限邊界** | 角色 A 嘗試執行只有角色 B 才能做的動作 | 一般用戶嘗試核准 |
| **跨實體一致性** | 兩個關聯物件屬於不同組織/公司/群組 | 不同公司的訂單與發票合併 |

## 五、通用 §6 畫面結構（依功能類型）

### 審批流程型
```
6.1  進入點（選單 / 快捷入口）
6.2  工作清單（搜尋 + 狀態篩選 + 分頁）
6.3  審核表單（標頭欄位 + 明細列表 + 摘要指標）
6.4  互動流程（狀態機轉換表）
6.5  確認 Modal / Toast 場景
6.6  流程圖（mermaid）
```

### 資料管理型
```
6.1  進入點
6.2  列表頁（搜尋/篩選/排序 + 分頁 + 批次操作）
6.3  詳情/編輯頁（欄位分群 + 必填標示 + 唯讀/可編輯切換）
6.4  新增/編輯互動流程（建立/儲存/刪除確認）
6.5  Modal / Toast / 空狀態
6.6  流程圖（可省略若邏輯簡單）
```

### 設定組態型
```
6.1  進入點
6.2  設定頁面（分群 tab 或 section + 說明文字）
6.3  編輯行為（即時儲存 / 明確「儲存」按鈕 + 取消確認）
6.4  生效時機（立即 / 重新整理 / 下次登入）
6.5  重設為預設值行為
```

### 分析儀表板型
```
6.1  進入點
6.2  全域篩選器（時間範圍 + 維度選擇）
6.3  指標卡（定義、計算方式、更新頻率）
6.4  圖表（圖表類型 + X/Y 軸定義 + Tooltip）
6.5  資料明細表（排序 + 匯出）
6.6  資料來源與更新時間顯示
```

## 六、通用錯誤訊息原則

格式：「{物件} {條件說明}，無法 {動作}。{建議動作（可選）}。」

| 情境類型 | 繁體中文模板 | English 模板 |
|---------|------------|-------------|
| 必填缺值 | `{欄位} 為必填，請輸入後再試。` | `{Field} is required.` |
| 格式錯誤 | `{欄位} 格式不正確，請輸入{格式說明}。` | `Invalid {field} format. Please enter {format}.` |
| 狀態限制 | `{已...狀態} 的 {物件} 無法 {動作}，請先 {前置動作}。` | `Cannot {action} a {status} {object}. Please {pre-action} first.` |
| 並發衝突 | `此 {物件} 已被他人修改，請重新載入後再試。` | `This {object} was updated by someone else. Please reload and try again.` |
| 超出上限 | `{欄位} 超過 {上限}，目前為 {實際值}。` | `{Field} exceeds {limit}. Current value: {actual}.` |
