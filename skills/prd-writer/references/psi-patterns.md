# Athena ERP PSI PRD 寫作慣例參考

> 此檔提取自 `docs/notion/銷貨/銷貨退回.md`（v6.x，1025 行）、`採購/採購單.md`（v4.x，809 行）等 7 份 PSI PRD。
> 適用範圍：進銷存（PSI）業務單據，部分規則也適用財務（AC）模組。
> **真相來源**：當本檔與 `docs/notion/` 下的實際 PRD 有出入時，以實際 PRD 為準。

## 1. 文件總體結構（11 大章節）

| 章節 | 標題 | 行數典型 | 核心產出 |
|------|------|---------|---------|
| §1 | 文件目的 | 3–8 行 | 一句話定義 + 背景說明 blockquote |
| §2 | 背景 | 15–30 行 | 現行問題 / 使用者需求 / 模組關聯 |
| §3 | 目標 | 10–25 行 | 目標一 ~ 目標 N（条列式） |
| §4 | 詞彙定義 | 20–40 行 | 三欄 table（名詞 / 說明 / 備註） |
| §5 | 使用者故事與驗收條件 | 80–130 行 | 5 個 Story + Edge Cases |
| §6 | 介面與流程 | 300–500 行 | 6.1~6.6 六子節 |
| §7 | 限制條件與範圍 | 20–40 行 | 範圍內 / 範圍外 / 業務限制 |
| §8 | 權限與稽核 | 20–35 行 | 角色矩陣 / 資料可見 / 稽核欄位 |
| §9 | 資料欄位規則 | 60–100 行 | 模型性質 / 框架欄 / 本模型欄 / 狀態轉換表 |
| §10 | 錯誤訊息文案 | 10–25 行 | 三欄 table（繁中 / English / 觸發情境） |
| §11 | 版本紀錄 | 5–20 行 | 四欄 table（版本 / 日期 / 修訂者 / 說明） |

### 文件開頭必有結構

```markdown
# {模組名稱}

> {一句話摘要：定義單據之完整生命週期}

> **命名說明**：本 PRD 一律以中文業務名稱表述功能、欄位、狀態、動作與錯誤情境；**文件中不出現任何程式代號**（程式 ID、資料模型／欄位名、method 名、錯誤碼 key、CSS class、狀態旗標、設定參數鍵與程式碼區塊）。後端開發之技術命名由工程師對應；§10 錯誤訊息僅列實際顯示文案。

---
```

## 2. 各章節格式細節

### §1 文件目的

```markdown
## 1. 文件目的

定義「{模組名}」之{核心功能}、{狀態機}、{關聯產出}，作為{模組}開發、測試與驗收依據。

> **背景說明**：本主檔於 {特徵編號} 階段（{日期}）建立。
```

### §2 背景

三段式結構：
1. **現行流程的問題**（bulleted list）
2. **使用者需求來源**（1~2 句）
3. **與其他模組的關聯**（bulleted list：模組名 → 關聯說明）

### §3 目標

```markdown
## 3. 目標

- **目標一**：建立{模型名}，含訊息追蹤（chatter）；支援{狀態機描述}。
- **目標二**：支援{業務路徑}；...
- **目標三**：...
```

每個目標約 1~3 句話，包含具體的技術行為。

### §4 詞彙定義

```markdown
## 4. 詞彙定義

| 名詞 | 說明 | 備註 |
| --- | --- | --- |
| {名詞} | {一句話說明} | {補充或空} |
```

**規則**：
- 約 12–19 個術語（業務單據通常 15+）
- 名詞 = 中文業務名（不用英文代號）
- 說明 = 精確的業務定義，避免循環定義
- 備註 = 補充條件、方向性說明（可空）
- **前幾行固定**：{本單名稱}、{主路徑}、{次路徑}、{核心明細名}、{關鍵業務術語}
- 末幾行固定：{傳票相關術語}、{反沖術語}（若有傳票）

### §5 使用者故事與驗收條件

```markdown
## 5. 使用者故事與驗收條件

### Story 1 — {描述：主要 Happy Path} — **{角色}**

**使用者故事**：作為**{角色}**，我想要{做什麼}，以便{得到什麼結果}。

**驗收條件**

- {具體可測試的條件，4–8 點}
- {每點以「系統...」或「{角色}...」為主語}

---

### Story 2 — ...
```

**標準 5 個 Story 主題（業務單據）**：
1. Story 1：主角色 Happy Path（建單 → 送簽 → 核准 + 核准產出）
2. Story 2：次路徑（若有結轉路徑：從來源單結轉）
3. Story 3：核准後動作（產傳票或下游連動）
4. Story 4：取消核准／解核（反向操作）
5. Story 5：公司隔離與可見性（多公司 + 角色權限）

**Edge Cases 格式**：
```markdown
### Edge Cases

- **{情境名稱（粗體）}**：{具體描述邊界條件與預期行為}。
- **{...}**：{...}
```
標準 8–12 條 Edge Cases，涵蓋：並發競爭、已作廢相關操作、跨公司驗證、金額為 0 的行、NULL 處理、限制 flag 的控制行為。

### §6 介面與流程

子節固定結構：

```
6.1  選單與進入點
6.2  List View（列表）
  6.2.1  工具列
  6.2.2  搜尋區
  6.2.3  欄位順序
  6.2.4  列表行為
  6.2.5  分頁器
6.3  Form View（表單）
  6.3.1  表單結構總覽
  6.3.2  Summary Card
  6.3.3  表頭分群欄位
  6.3.4  明細 Section（含 Drawer 規格）
  6.3.5  表單底部操作列（Footer）
  6.3.6  Smart Bar（智慧列）
6.4  互動流程（狀態機轉換文字說明 + 表格）
6.5  Modal / Toast 場景
6.6  流程圖（mermaid 圖）
```

**§6 命名規則（嚴格）**：
- 欄位一律**中文業務名**（不寫欄位代號如 `sale_id`、`partner_id`）
- M2O 來源寫「`Dropdown`（M2O 銷貨單）」而非 「`Dropdown`（`psi.sale_order`）」
- 系統參數寫「系統參數『銷貨退回日記帳』」而非 `psi_sale_return_journal_id`
- 可保留的英文詞：`List`、`Form`、`Drawer`、`Stepper`、`Summary Card`、`Smart Bar`、`toast`、`modal`、`chip`、shared UI 元件名（`TextBox`、`Dropdown`、`DataGrid`、`DatePicker`等）
- `action_submit`、`action_approve` 等 action 名**保留**（§6.4 互動流程可用）

**§6.2.1 工具列格式**（table）：
```markdown
| 狀態 | 左群 | 右群（固定） |
| --- | --- | --- |
| 未勾選 | 「新增{單}」（主要按鈕）＋「匯入」（外框） | 分群下拉 ＋ 「⚙ 設定」 |
| 已勾選 N 筆 | 「↓ 匯出選取項」＋「🗑 刪除所選草稿」（條件顯示）＋「已選取 N 筆 ×」標籤 | 同上 |
```
**PSI 慣例**：無批次作廢（草稿=物理刪除 unlink、已提交以上=作廢 voided）。

**§6.2.2 搜尋區格式**（table）：
```markdown
| 欄位（label） | 元件 | 響應式優先序 | 預設值 / 限制 |
| --- | --- | --- | --- |
| {單號} | `TextBox` | 最高 | 空；按 Enter 觸發查詢 |
| ... | ... | ... | ... |
| 狀態 | `Dropdown` | 最高 | **第一選項固定「全部」（空值）** |
```
PSI 慣例：5 個 filter（單號 / 對象 / 經辦人 / 日期區間 / 狀態），精簡不超過 6 個。

**§6.2.3 欄位順序格式**（table，9–11 欄）：
```markdown
| # | 欄位 | 元件 | 對齊 | 凍結 | 最小寬度 | 說明 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | ☐ 勾選 | `Checkbox` | 置中 | 凍結左 | — | 全選 |
| 2 | {主鍵單號} | `Link` | 靠左 | 凍結左 | 200px | ... |
| ... |
| N | 操作 | `IconButton` | 置中 | 凍結右 | 56–96px | ... |
```
PSI 慣例：金額僅留一欄**含稅總額**（不放未稅/稅額），tfoot 合計單欄帶標籤前綴（如 `採購合計: {Σ}`）。

**§6.3.2 Summary Card 格式**（PSI 業務單據標準）：
- 左側：金額**等式橫向排列**「未稅金額 ＋ 稅額 ＝ 總金額」（總金額為主指標放大）
- 金額列右側：「已產生傳票號碼」chip（綠色，有關聯傳票時顯示）
- 右側：3 步 Stepper（草稿 / 已提交 / 已核准）；`voided` 整條換紅底 `voided-banner` pill

**§6.3.3 表頭分群欄位格式**（table，7 欄標頭）：
```markdown
| # | 欄位 | 元件 | 必填 | 新增 | 已提交（有限編輯） | 凍結期（已核准起） | 說明 |
```
三態欄位狀態：新增（可改）、已提交（有限編輯）、凍結期（唯讀）。

## 3. PSI 特定寫作慣例

### 3.1 狀態機命名（固定）

| 狀態 | 名稱 | 備註 |
|------|------|------|
| `draft` | 草稿 | 可全編輯 |
| `submitted` | 已提交 | 有限編輯（特定欄位鎖定） |
| `approved` | 已核准 | 全唯讀；後端三層防禦 |
| `voided` | 已作廢 | 終態；軟刪除（停用） |

| 動作 | 方法命名 | 說明 |
|------|---------|------|
| `action_submit` | 提交（送簽） | 草稿 → 已提交，取號 |
| `action_approve` | 核准 | 已提交 → 已核准，觸發核准連動 |
| `action_unapprove` | 取消核准（解核） | 已核准 → 已提交，逆向操作 |
| `action_void` | 作廢 | 已提交/已核准 → 已作廢 |

**取號時機兩種**：
- **送簽取號**：草稿為空（顯示「/」），送簽時系統取號。多數採購類單據。
- **草稿首存取號**：草稿首次儲存即配號，後續各動作維持原號。銷貨退回、部分銷貨類單據。

### 3.2 Header 欄位三區模型（PSI 業務單據）

識別區（首） → 決策區（中段） → 隔離區（末）

**識別區**（最前，固定）：
- 本單單號（第 1 格，唯讀，新增顯「/」）
- 來源單號（緊接）

**決策區**（中段，照先決順序）：
- 對象（供應商/客戶）→ 單據類型 → 經辦人 → 日期
- **經辦人固定排在日期前**（採購人員→採購日期、業務員→退回日期）

**隔離區**（末，固定）：
- 帳簿（日記賬） → 應付/應收科目 → **公司別**（唯讀帶入，壓末）→ 幣別

### 3.3 結轉 + 產傳票慣例（Wizard-less）

**結轉帶入明細**（不做結轉精靈）：
- 表頭選定「原來源單」時 onchange 自動帶入可○量 > 0 的明細
- 帶入後數量欄預設 0，於 Drawer 逐筆輸入
- 儲存時自動移除數量 0 的行
- 驗證點：Drawer 即時 + 送簽 + 核准（三重驗證）

**產生傳票**（不做產傳票精靈）：
- Footer「建立傳票」直接按鈕
- primary confirm modal → 直接產生，無分錄預覽
- 日記帳/科目/日期/摘要系統自動取值
- 按科目（如銷貨原因之科目）分組產出多分錄

### 3.4 Summary Card 格式（PSI 業務單據）

- 左側：**金額等式橫向排列**「未稅金額 ＋ 稅額 ＝ 總金額」
- 金額列右側：「已產生傳票號碼」chip（有傳票才顯示）
- 右側：3 步 Stepper（草稿/已提交/已核准）；voided 換 voided-banner 紅底 pill

### 3.5 List 欄位慣例

| 欄位 | 規則 |
|------|------|
| 金額 | 僅留**一欄含稅總額**，tfoot 合計帶標籤前綴 |
| 欄數 | 9–11 欄（checkbox + PK + 4–6 資料欄 + 狀態 + 操作） |
| 批次操作 | 無批次作廢；有批次刪除草稿（條件顯示）+ 匯出選取項 |

## 4. 財務模組（AC）欄位排序差異

財務模組 header 採**雙列模型**（與 PSI 三區不同）：

| 列 | 欄位 |
|----|------|
| 第一列（業務） | 單號 → 對象 → 主日期 → 次日期 → 產生方式 |
| 第二列（後台） | 公司別 → 部門 → 稅務公司 → 幣別 |

> PSI 的公司別在末尾；AC 的公司別在第二列首位。寫混用模組時注意區分。

## 5. 常用 §5 Edge Cases 類型

每份 PSI PRD 至少涵蓋：
1. **並發競爭**：兩人幾乎同時操作同一筆資料的結果
2. **作廢已產傳票**：已核准已產傳票欲作廢，須先手動反沖
3. **金額/數量為 0 的行**：行內 0 值的暫存 vs 送簽/核准時移除
4. **跨公司驗證**：退回單/採購單與來源單必須同公司
5. **NULL / 未設定主檔**：客戶/供應商未設科目、未設分類時的三層 fallback
6. **狀態不一致**：已作廢的關聯單欲繼續操作時的擋下行為
7. **限制 flag 控制**：某 boolean 旗標（如「入應收」）為 false 時，相關功能整組停用

## 6. 典型 §10 錯誤文案格式

| 情境類型 | 繁體中文格式 | English 格式 |
|---------|------------|-------------|
| 必填缺值 | `{單據名} 有 {N} 條明細未設定{欄位名}，無法{動作}。` | `{Record} has {N} line(s) without {field}. Cannot {action}.` |
| 關聯不一致 | `{欄位A} 必須與{來源}一致。` | `{Field A} must match {source}.` |
