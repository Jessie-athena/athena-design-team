# ERP 介面文案審查

依 ux-writer skill 的 4 個核心原則（Clear / Concise / Useful / Human）、Voice & Tone 框架與常見 Copy Pattern 逐條審查。

---

## 1.『確定要刪除嗎？』

**判定：需修改**

問題：
- **Concise / Clear 不足**：沒講「刪除的是什麼」，使用者無法確認自己刪對東西。
- **危險動作缺後果說明**：刪除屬破壞性操作，依 Confirmation pattern 須補「後果說明 + CTA」，並提醒無法復原。
- 句型偏口語問句，缺乏對象與行動引導。

**建議改法（Confirmation pattern：動作描述？＋後果說明＋CTA）：**

```
刪除此筆採購單？
刪除後將無法復原。
[取消] [刪除]
```

> 對象（「採購單」）請依實際 ERP 單據替換。CTA 按鈕直接用動詞「刪除」明示破壞性。

---

## 2.『載入中...』

**判定：需修改**

問題：
- **不夠具體**：依 Loading pattern，「正在建立專案...」勝過「載入中...」，應說明正在做什麼。
- **標點錯誤**：使用了半形 `...`，繁中應用全形刪節號「⋯⋯」或省略號「…」。
- 補充：依規範 loading 文字只在 > 3s 才顯示，太快出現反而讓人焦慮。

**建議改法（具體 + 正確標點）：**

```
正在載入資料…
```

> 若情境明確，建議再具體化，例如「正在查詢採購單⋯」「正在產生報表⋯」。

---

## 3.『刪除成功！🎉』

**判定：需修改**

問題：
- **Tone 不符**：成功 tone 應「輕快肯定」而非歡慶；刪除是破壞性動作的結果，慶祝用 emoji 與情境衝突（emoji 較適合 empty state 鼓勵情境，如「收件匣清空囉 🎉」）。
- **驚嘆號過度**：B2B 操作回饋不需要驚嘆號，顯得不夠專業沉穩。
- **Concise**：可更精簡，動作完成回饋用「已…」句型即可。

**建議改法（成功 tone：輕快肯定）：**

```
已刪除
```

> 與 skill 範例「已儲存」一致，採「已 + 動詞」的完成式回饋句型，不加 emoji、不加驚嘆號。

---

## 4.『點這裡清除篩選』

**判定：需修改**

問題：
- **a11y 不合格**：依 a11y 注意事項，button 文字要有意義，「點這裡」是反例，螢幕閱讀器使用者無法得知作用。
- **Concise**：「點這裡」是贅字，動作本身已是可點擊元素。
- 應改為動詞 + 對象的按鈕命名。

**建議改法（動詞 + 對象，去除「點這裡」）：**

```
清除篩選
```

> 與 Empty State pattern 範例「沒有符合條件的結果，[清除篩選]」一致。

---

## 5.『送審』

**判定：OK（可微調確認一致性）**

說明：
- 符合 Button pattern：動詞開頭、2 字、簡潔明確，是 ERP 常見且使用者熟悉的動作詞。
- **唯一提醒**：需與 Copy Doc 動作命名規則維持跨 screen 一致。若系統其他處用「提交審核」「送出審核」，應統一擇一，避免同義詞混用。
- 若 button 空間允許且想更明確，可用「送出審核」；但「送審」在 ERP 語境下已通用，維持原樣即可。

**建議：維持「送審」，並登錄至 Copy Doc 術語表確保全站一致。**

## 審查總結

| # | 原文 | 判定 | 建議 |
|---|------|------|------|
| 1 | 確定要刪除嗎？ | 需修改 | 刪除此筆採購單？／刪除後將無法復原。／[取消] [刪除] |
| 2 | 載入中... | 需修改 | 正在載入資料…（標點改全形、盡量具體化） |
| 3 | 刪除成功！🎉 | 需修改 | 已刪除（去 emoji、去驚嘆號） |
| 4 | 點這裡清除篩選 | 需修改 | 清除篩選（去「點這裡」，符合 a11y） |
| 5 | 送審 | OK | 維持，登錄 Copy Doc 確保一致 |

**共通問題提醒：**
- 標點：繁中用全形標點，刪節號用「⋯⋯／…」而非半形 `...`。
- emoji / 驚嘆號：B2B 操作回饋保持專業沉穩，慎用。
- a11y：按鈕文字須自帶意義，避免「點這裡」。
- 一致性：所有動作詞（送審／刪除／清除…）應收錄 Copy Doc，跨 screen 統一。
