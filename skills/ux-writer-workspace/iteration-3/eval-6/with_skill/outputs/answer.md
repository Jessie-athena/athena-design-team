# 出貨阻擋訊息：業務版 vs 倉管版

> 情境：銷貨訂單／出貨單欲出貨，但庫存不足而被系統阻擋。
> 屬「驗證／阻擋類」可預期業務阻擋 → 套用 ERP 事務性句型 `無法[動作]：[原因]`，原因要具體、給下一步，不丟技術碼、不責備使用者。

---

## 給業務看的版本

> 出現位置：銷貨訂單／出貨作業，業務按下「出貨」時。

```
無法出貨：『辦公椅 OC-200』庫存不足，訂單需求 50，目前可出 30
請與倉管確認補貨或調整出貨數量後再試
```

如需多列明細，可改條列：

```
無法出貨：以下品項庫存不足，請與倉管確認補貨或調整出貨數量
・辦公椅 OC-200：需求 50，可出 30
・會議桌 MT-100：需求 20，可出 12
```

---

## 給倉管看的版本

> 出現位置：出庫／揀貨作業，倉管執行出庫扣帳時。

```
無法出庫：『辦公椅 OC-200』於〔台中倉〕庫存不足，本次需扣 50，現有可用 30
請先入庫補足或自其他地點調撥後再出庫
```

如需多列明細，可改條列：

```
無法出庫：以下品項於〔台中倉〕庫存不足，請補足或調撥後再出庫
・辦公椅 OC-200：需扣 50，現有可用 30
・會議桌 MT-100：需扣 20，現有可用 12
```

---

## 為什麼兩者寫法不同

兩則描述的是**同一個阻擋事件**，但讀者的任務流程、心智模型與焦慮點不同，所以**動詞、資訊粒度、下一步指引**都跟著換。這正是 SKILL §1～§2「先讀懂使用者、寫到他的心智模型」的要求——不寫一句想通吃。

| 面向 | 業務 | 倉管 |
|---|---|---|
| **心智模型** | 「把這張單順利出掉、別漏出貨給客戶」——以訂單與客戶進度為主軸 | 「實際庫存 vs 帳面數量」——每個動作都會動到某地點的數量 |
| **最在意 / 焦慮** | 會不會漏出貨、能不能如期交付客戶 | 料帳是否一致、是哪個料、哪個地點、差多少 |
| **動詞用詞** | 「出貨」——業務每天講的是出貨給客戶 | 「出庫」——倉管講的是庫存地點的扣減動作 |
| **資訊粒度** | 給到「需求 vs 可出數量」即可，無須地點細節 | 必須帶**地點**（〔台中倉〕）與「可用量」，因為倉管要按地點處理料帳 |
| **下一步** | 不在倉管職權內，導向「與倉管確認補貨／調整數量」 | 在自己職權內，直接給「入庫補足或自其他地點調撥」 |

關鍵差異收斂成一句：**業務要的是「對客戶交付的影響 + 找誰處理」，倉管要的是「動到哪個地點的料帳 + 自己怎麼補」。** 用詞（出貨／出庫）對齊各自慣用詞彙，下一步指引各自落在其職權範圍內，使用者才不會看到一個自己無從下手的指令。

### 共同遵守的慣例
- **句型一致**：兩則皆為 `無法[動作]：[原因]`（驗證／阻擋類事務句），不混用系統錯誤的安撫句型。
- **括號**：品項名等引用 UI／動態值用 `『』`；句中可點擊的地點篩選用 `〔〕`（倉管版的〔台中倉〕可點擊跳該地點庫存）。
- **阿拉伯數字 + 具體數量**：講清需求與可出／可用量，不寫「庫存不足，請稍後」這種無從行動的模糊話。
- **不責備、不丟技術碼**：描述「狀態 + 行動」，講使用者懂的因果，不報內部例外。
- **i18n**：數量用 `Label: Value`（需求 50／可出 30）結構、一句一語意，避免句中變數造成翻譯破版。
