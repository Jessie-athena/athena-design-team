# 出貨阻擋訊息 — 業務 vs 倉管

> 情境：ERP 出貨時庫存不足，無法出貨。屬於**驗證／阻擋類**錯誤（可預期的業務阻擋），套用德安 ERP 事務性句型 `無法[動作]：[原因]`，並依角色補不同的下一步。

---

## 給「業務」看的訊息

```
無法出貨：庫存不足
可出貨數量 3，本次需求 10。請調整出貨數量，或〔通知倉管補貨〕。
```

- 標題：`無法出貨：庫存不足`
- 內文以 `Label: Value` 結構列出可出貨數量與需求數量，避免句中變數、預留多語系空間。
- inline CTA 用 `〔〕`：`〔通知倉管補貨〕`。

## 給「倉管」看的訊息

```
無法出貨：庫存不足
品項『A-1001 不鏽鋼螺絲』可用庫存 3，需出貨 10，缺 7。請確認實際庫存後〔補登入庫〕或〔調整安全庫存〕。
```

- 標題同為 `無法出貨：庫存不足`（跨角色標題一致，便於溝通同一張單）。
- 內文點名品項（`『…』`引用品名）、給出缺口數量，並提供倉管職權內的兩個下一步：`〔補登入庫〕`、`〔調整安全庫存〕`。

---

## 為什麼兩者寫法不同

兩則的**狀態描述相同**（都是「無法出貨：庫存不足」），差別在**下一步行動**，因為文案的「行動導向」原則要求在阻塞情境給使用者能執行的下一步，而**業務與倉管的職權與能解決的方式不同**：

1. **CTA 對應各自能做的事**
   - 業務無權異動庫存，他能做的是改數量或把問題轉給倉管，所以 CTA 是「調整出貨數量／通知倉管補貨」。
   - 倉管掌管實體庫存，他能做的是補登入庫、調整安全庫存，所以 CTA 指向庫存作業，而非「改出貨單數量」（那不是他的單）。
   - 把對方做不到的動作寫進 CTA，等於給了一條死路，違反「給下一步」與「不責備使用者」原則。

2. **資訊顆粒度對應各自的決策需求**
   - 業務只要知道「能出多少 vs 要出多少」就能決定改量或求援，不需要品項細節。
   - 倉管要實際處理庫存，必須看到**是哪個品項、缺多少**，才知道補哪一項，所以多帶品名與缺口數量。

3. **共用的底線一致**
   - 兩則都用同一個事務性句型 `無法[動作]：[原因]`、同一個標題、`Label: Value` 結構、`〔〕` inline CTA、`『』` 引用元素名——維持跨角色、跨單據的一致性，只在「下一步」這一段按角色分流。
   - 兩則都不丟技術碼、不責備使用者、不過度安撫（這是**阻擋類**而非系統異常，不需「請稍後再試」那種同理安撫語氣）。

> 一句話：**相同的阻擋狀態，分流到各角色「做得到的下一步」**——這是同一情境寫兩則訊息的唯一理由，不是為了換句話說。
