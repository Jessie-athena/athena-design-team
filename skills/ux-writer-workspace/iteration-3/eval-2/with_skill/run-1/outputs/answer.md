# ERP 介面文案審查

對象產品線：德安 ERP（財務／進銷存）；讀者多為會計、倉管、採購、業務等專業從業者。審查依據：ERP 單據慣例（狀態機、`〔〕/『』/「」` 括號、`無法[動作]：[原因]`、`已[動作] N 筆`）、通用寫作原則（清晰／簡潔／給下一步／不裝可愛、無 emoji）、a11y。

---

## 1. 『確定要刪除嗎？』

**判定：需改**

問題：

- 破壞性確認句型不對。ERP 慣例為 `[後果說明]，是否繼續？`，要先講後果（不可復原），目前只有空泛問句。
- 動詞模糊、無動作導向 CTA。彈窗按鈕應用明確動詞，不用「確定／OK」這類中性詞。
- 沒對齊使用者「可逆心智」：草稿可物理刪除（用「刪除」），已提交／已核准只能留痕作廢（用「作廢」）。一句通吃會誤導。

建議改為（依情境二擇一）：

- 刪除草稿：
  ```
  刪除後無法復原，是否繼續？          [取消] [刪除]
  ```
- 已成立單據（已提交／已核准）：
  ```
  作廢後無法復原，是否繼續？          [取消] [作廢]
  ```

> 若是批次刪除草稿，可在後果前帶數量：「將刪除 N 筆草稿，刪除後無法復原，是否繼續？」

## 2. 『載入中...』

**判定：需改**

問題：

- 籠統。慣例「具體優於籠統」，要講正在做什麼，讓使用者知道在等什麼。
- 標點錯誤。中文文案應用全形刪節號「…」，不用半形三點「...」。
- 顯示時機：< 3 秒不該顯示 loading 文字（太快反而焦慮），由前端控制 ≥ 3 秒才顯示。

建議改為（依實際動作具體化）：

```
正在查詢…
正在產生報表…
正在產生傳票…
```

> 若情境確實無法具體化，至少改標點為「載入中…」；但優先具體描述動作。

---

## 3. 『刪除成功！🎉』

**判定：需改**

問題：

- 含 emoji。B2B 工具一律不放 emoji、不裝可愛。
- 消費級驚嘆口吻（「成功！」）。ERP Toast 應事務性、簡潔肯定。
- 未用 Toast 標準句型 `已[動作] N 筆`；批次操作應帶數量讓使用者確認筆數。

建議改為：

- 單筆：
  ```
  已刪除
  ```
- 批次：
  ```
  已刪除 N 筆草稿
  ```

> 此為低阻斷即時回饋，用 Toast（自動消失、無按鈕），不要用彈窗。

---

## 4. 『點這裡清除篩選』

**判定：需改**

問題：

- a11y 違規。連結／按鈕文字要有意義，禁止用「點這裡」這類無語意指示文字（螢幕報讀與 SEO 都失效）。
- 句中可點擊動作的括號慣例未套用。ERP 句中 inline CTA 用 `〔〕`，不用「點這裡」或 `[方括號]`。
- 「清除篩選」本身是既有動作詞（正確，沿用），問題只在外層包裝。

建議改為：

- 純按鈕（連結文字即動作本身）：
  ```
  清除篩選
  ```
- 若是句中引導（空狀態／無結果時）：
  ```
  查無符合條件的資料，請調整搜尋條件或〔清除篩選〕
  ```

---

## 5. 『送審』

**判定：需改**

問題：

- 偏離強制狀態機命名。德安 ERP 狀態流轉 `草稿 → 已提交 → 已核准`，對應動作按鈕固定為「提交」「核准」，沒有「送審」。「送審／審核／取消審核」屬自創，會與其他單據不一致。
- 慣例規定：偏離此命名必須在交付訊息註明理由；此處無特殊理由，應正規化。

建議改為：

```
提交
```

> 對應動作：提交（draft→submitted）／核准（submitted→approved）／解核（approved→submitted）／作廢。若該模組業務上確有「送審」獨立語意（非單純提交），須回 PM 確認並在交付說明理由，否則一律用「提交」。
