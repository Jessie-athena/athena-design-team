# 研究合成報告 — 自訂報表功能（8 場訪談，2026-05）

> 角色：UX Researcher（Discover/Define 階段）
> 方法：半結構化深度訪談 × 8，Affinity mapping 合成
> 研究問題：使用者實際的報表工作流程為何？為什麼不用自訂報表（月活躍率僅 12%）？

---

## 0. 樣本與限制（必須先讀）

| 項目 | 內容 |
|------|------|
| 樣本 | 8 位客戶端使用者（營運/財務職），使用產品 6 個月以上 |
| 招募來源 | CS 推薦 6 位 + 自行報名 2 位（P3、P7） |

**已知偏誤（解讀洞察前必須納入）：**
1. **CS 推薦的 6 位均為近三個月開過客服工單的客戶** → 樣本偏向「遇過問題」的使用者，痛點強度可能被高估。
2. **P1、P5 為同公司**（占 2/8）→ 兩人的工作流程與「信任缺口」敘事高度相關（P5 流程是 P1 教的），證據力應視為 1.5 個獨立來源而非 2 個。
3. **自行報名的 P3、P7 偏重度/技術型使用者** → 自選樣本，其需求不代表一般使用者。
4. **原訂第 9 場高階主管臨時取消未補** → 決策者視角僅有 P6（財務主管）、P7（IT 代決策）兩個間接樣本。

## 1. Affinity Mapping 總覽

| 主題群 | 涵蓋受訪者 | 一句話 |
|--------|-----------|--------|
| A. 既有工作流程根深蒂固 | P1, P2, P5, P8 | 「匯出 CSV → Excel 手動整理」是預設路徑，每週/每月重複耗時 |
| B. 對系統數字的信任缺口 | P1, P5, P6 | 不信任數字一致性，是「敢不敢改用」的前置條件 |
| C. 功能能見度與入口問題 | P2, P8（+P1 部分） | 2/8 從未聽過此功能；入口藏在「進階」選單第三層 |
| D. 第一步就卡關的概念語言 | P4（+P1） | 資料來源命名（交易明細 vs 結算紀錄）是系統視角，不是使用者視角 |
| E. 範本無法共享/鎖定 | P3, P6 | 重度使用者與主管都指向「組織級報表定義」的缺口 |
| F. 採用決策不在末端使用者手上 | P5, P7, P8 | 末端使用者沒有改流程的權限或動機，採用是由上而下的 |
| G. 進階使用者的天花板 | P3, P7 | timeout、功能太陽春、寧可走 API + BI |

## 2. Insight Cards

### Insight #1
**洞察標題**：低使用率的首要解釋不是「功能不好用」，而是「使用者根本不知道它存在、或第一步就看不懂」。

**證據**：
- P2：「這在哪裡？我每天用的頁面沒看過這個。」（訪談中才第一次知道；入口在「進階」選單第三層）
- P8：沒聽過自訂報表功能
- P4：「它問我要選什麼資料來源，我哪知道『交易明細』跟『結算紀錄』差在哪，我就是要昨天的營業額而已。」
- P1：試過一次，「存檔之後下次進來找不到我存的範本在哪」，從此放棄

**Why it matters**：在討論任何功能增強之前，獲取漏斗的最前段（發現 → 第一次成功）就已斷裂。4/8 受訪者卡在「不知道」或「第一次嘗試失敗」，這類問題修復成本低、對 12% 月活躍率的槓桿大。

**How might we**：
- HMW 讓常做匯出的使用者在匯出當下發現自訂報表 by 在匯出 CSV 流程中嵌入入口/引導？
- HMW 讓非分析背景的使用者選對資料來源 by 以「我要看什麼」（昨日營業額、本月結算）的任務語言取代資料表命名？

**信心水準**：高（4/8 獨立證據，涵蓋不同公司與產業；且有客觀事實佐證——入口確實在三層選單內）

---

### Insight #2
**洞察標題**：「數字一致性」是信任門檻——使用者不是嫌工具難用，而是不敢承擔數字錯誤的責任。

**證據**：
- P1：「之前有一次匯出來的加總跟畫面上不一樣，從那次之後我就不敢直接用了。」（事件約半年前未再發生，但習慣已固化）
- P5：看完示範後第一個問題是「那它做出來的數字跟匯出 CSV 會一樣嗎？」；「錯了算我的」
- P6：「上個月有兩個人給我同一張報表但數字不同，查了一天……工具的問題其次，流程不統一才是我的痛。」

**Why it matters**：B2B 報表的核心 job 不只是「產出表格」，而是「交出去的數字經得起追問」。只要使用者對工具產出的數字有一絲懷疑，就會退回可以逐格核對的 Excel。功能再強，不解決信任問題就不會有遷移。
（注意：P1/P5 同公司，此主題的獨立來源實為 2 家公司。）

**How might we**：
- HMW 讓使用者驗證自訂報表與匯出資料一致 by 提供「與畫面/匯出數字對帳」的可見保證或對照檢視？
- HMW 讓主管確保全公司用同一套數字定義 by 可鎖定篩選條件的組織級範本？

**信心水準**：中高（3 位受訪者、2 家獨立公司；與 Insight #4 互相增強）

---

### Insight #3
**洞察標題**：採用決策權不在末端操作者手上——他們執行別人定的流程，沒有動機也沒有權限改變工具。

**證據**：
- P5：「P1 怎麼做我就怎麼做……我不敢自己改流程，錯了算我的。」
- P8：「那個範本是主管的，我不能改。」「不要叫我學新東西，我事情已經夠多了。」
- P7：替公司 30 個使用者做工具決定，「個別使用者沒有選擇權」
- P6：自己不操作，但「如果範本能鎖定條件、全公司用同一份定義，我馬上要求大家改用」

**Why it matters**：把末端使用者當成採用對象的推廣策略（教學、tooltip）天花板很低。真正的採用槓桿在「定義流程的人」——主管（P6）、團隊分析師（P3）、IT 管理員（P7）。一個 P6 級的決策可以一次帶進整個團隊。

**How might we**：
- HMW 讓流程制定者（主管/分析師）把報表定義一次性推送給整個團隊 by 範本共享 + 條件鎖定？

**信心水準**：高（4/8，跨 4 家公司，且包含決策者與被決策者兩側的一致敘事）

---

### Insight #4
**洞察標題**：「範本共享 + 條件鎖定」是重度使用者與管理者共同指向的最大功能缺口，也是擴散機制本身。

**證據**：
- P3（重度使用者，23 個範本）：「範本不能分享給同事，業務問我要報表，我只能截圖教他自己設一次，他設到一半就放棄回來找我。」
- P6：「如果範本能鎖定條件、全公司用同一份定義，我馬上要求大家改用。」

**Why it matters**：這個缺口同時卡住三件事：(1) P3 這類內部多重使用者（servicing 5 個部門）無法把工作放大；(2) P6 的數字一致性需求無解；(3) 產品失去「一人設定、全團隊使用」的自然擴散路徑——這直接解釋為什麼月活躍率停在 12%：目前每個使用者都必須自己從零學會設定。

**How might we**：
- HMW 讓 P3 型分析師把範本變成團隊資產 by 範本分享（唯讀/可複製兩種權限）？
- HMW 讓 P6 型主管消除報表定義分歧 by 管理員可鎖定篩選條件的「官方範本」？

**信心水準**：中（僅 2 位直接證據，但兩位分屬「製作者」與「決策者」互補角色，且與 Insight #2、#3 三角驗證；P3 為自選樣本須留意）

---

### Insight #5
**洞察標題**：使用者要的終點不是「報表編輯器」，而是「固定報表自動出現在該出現的地方」。

**證據**：
- P1：「報表自己跑好，每週一寄到我信箱。」
- P8：「如果系統能直接吐出主管要的那張表，當然好啊。」
- P2：月結 4 張「固定」報表；P1/P5 的週報格式也是固定的——重複性高、變動性低

**Why it matters**：受訪者的報表需求絕大多數是**週期性固定報表**，不是探索式分析。自訂報表目前的定位（每次進來手動跑）跟真實 job（每週一早上要交出去）之間有結構性錯位。排程寄送把「使用功能」變成「收到結果」，可同時繞過能見度（Insight #1）與學習成本的障礙。

**How might we**：
- HMW 讓週報製作者不再每週手動重做 by 範本排程 + Email 寄送？

**信心水準**：中高（直接訴求 2 位，行為證據 4 位均為固定週期報表）

---

### Insight #6
**洞察標題**：進階/技術型使用者有明確天花板——效能上限與 API 文件，硬留他們在 UI 內是錯的方向。

**證據**：
- P3：「跑超過三個月的資料會 timeout，我只好拆成三段跑再自己接起來。」
- P7：「你們的報表功能我看過，對我來說太陽春……與其做報表編輯器，不如把 API 的欄位文件寫清楚。」
- P2：匯出 CSV 欄位名稱是英文代碼，每次要對照表翻譯（資料介面品質的旁證）

**Why it matters**：P7 型客戶（有 BI 系統）不是自訂報表的目標客群，試圖用編輯器功能爭取他們是浪費；但 API 文件與欄位命名品質影響的是整個資料出口（含 CSV 匯出），是低成本高滿意度的修繕。P3 的 timeout 則是留住唯一重度使用者原型的底線問題。

**How might we**：
- HMW 讓資料順利流出系統 by 補齊 API/匯出欄位的中文對照文件？

**信心水準**：中（2 位直接證據，且均為自選樣本，須以量化資料驗證 P7 型客戶占比）

## 3. 反證與張力（誠實揭露）

- **「工具再好我也要重學」（P2）**：對 Excel 高手而言，遷移成本永遠高於現狀成本。即使做完所有改善，P2 型使用者可能仍不遷移——除非主管要求（接回 Insight #3）。不應以「全員改用自訂報表」為成功定義。
- **P7 的建議與功能投資方向相反**：他主張別做編輯器。這提醒我們先用量化資料分段：有 BI 的客戶（API 路線）vs 沒有 BI 的客戶（UI 路線），兩條路線不該互相妥協。
- **P1 的信任事件是半年前的單一事件且未再發生**：信任問題部分是「歷史傷痕」而非現行 bug，解法偏向「可驗證性的設計」而非修錯。

## 4. 優先順序建議（接下來該做什麼）

依「對 12% 活躍率的槓桿 × 證據信心 × 實作成本」排序：

### 第一優先：範本共享 + 條件鎖定（組織級官方範本）
- 對應 Insight #3、#4、#2。一個功能同時解決擴散機制、數字一致性、決策者採用三件事，是唯一能把採用模式從「人人自學」翻轉成「一人設定、全團隊用」的槓桿。
- 建議形式：範本可分享（唯讀/可複製）、管理員可鎖定篩選條件、團隊範本庫。
- 風險低：P3（製作端）與 P6（決策端）的需求陳述高度一致。

### 第二優先：範本排程寄送（每週自動 Email）
- 對應 Insight #5。把使用門檻降為零，直接命中「週期性固定報表」這個真實 job；與第一優先疊加後形成「主管定義範本 → 全團隊每週自動收到」的完整故事。

### 第三優先：能見度與第一哩路修繕（成本最低，可立即做）
- 對應 Insight #1：
  1. 入口從「進階」第三層移出，並在匯出 CSV 流程嵌入引導
  2. 資料來源改用任務語言命名（或加白話描述）
  3. 修復「存檔後找不到範本」的路徑問題
- 這批是 quick win，不需等大功能即可動工。

### 第四優先：信任與可驗證性
- 對應 Insight #2：提供自訂報表數字與匯出/畫面數字的一致性保證（如對帳檢視、同一計算引擎的明示）。可與第一優先一起設計（鎖定條件本身就是一致性機制）。

### 平行低成本項：API / 匯出欄位文件 + 中文對照（Insight #6）
- 交給文件/平台團隊平行處理，不占設計主線資源。

### 後續研究缺口（建議補做）
1. **補 1-2 場高階主管/決策者訪談**（原第 9 場取消），驗證 Insight #3/#4 的決策端假設。
2. **量化驗證**：請 data-analyst 拉（a）匯出 CSV 的使用頻率與週期性分布、（b）自訂報表的漏斗（進入 → 選資料來源 → 存檔 → 二次使用）斷點、（c）客戶端有無 BI 系統的占比——對應本報告各洞察的信心升級。
3. **招募校正**：下輪納入未開過工單的客戶，平衡 CS 推薦偏誤。
