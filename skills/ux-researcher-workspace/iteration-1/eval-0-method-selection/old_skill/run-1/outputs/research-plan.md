# Research Plan — B2B 後台「自訂報表」低使用率診斷 × 每週營運報表工作流程研究

> 角色：🔬 UX Researcher｜研究類型：混合（Generative 探索 + Evaluative 診斷）
> 日期：2026-06-10

---

## 1. 研究背景

B2B 後台的「自訂報表」功能上線後使用率偏低。產品團隊想知道：

- 為什麼使用者不用自訂報表？（是不知道、不會用、不信任，還是不需要？）
- 使用者目前實際上是怎麼完成每週營運報表的？（真實 workflow、繞道行為、工具拼接）

這兩題本質不同：前者是**針對既有功能的診斷型問題**，後者是**針對工作流程的探索型問題**。單一方法無法同時回答，因此採混合設計。

## 2. 研究目標

1. **G1（探索型）**：理解使用者每週營運報表的完整工作流程——從資料來源、整理加工、到產出與發送的每一步，以及其中的工具、繞道（workaround）與痛點。
2. **G2（診斷型）**：找出自訂報表功能在使用者 workflow 中缺席的原因——是認知問題（不知道）、能力問題（不會設定）、信任問題（資料不對／不敢用）、還是適配問題（功能做不到他們要的）。
3. **G3（機會辨識）**：辨識自訂報表若要進入每週報表 workflow，需要補上哪些缺口（HMW 形式輸出，交棒 product-strategist / interaction-designer）。

> 自檢：三個目標都是「為什麼／怎麼做」的開放式問題，可被訪談與觀察回答，非 yes/no、非數量題。✅

## 3. 研究方法選擇

### 3.1 方法決策

| 候選方法 | 適合回答 | 採用？ | 理由 |
|---------|---------|-------|------|
| **脈絡訪查（Contextual Inquiry）** | G1 工作流程 | ✅ 主方法 | 報表流程是「做出來」而非「說出來」的——使用者口述常遺漏 Excel 拼接、手動複製等繞道行為。在使用者實際做週報的當下觀察，才能看到真實 workflow。 |
| **半結構化深度訪談 + 現場任務回顧** | G2 低使用率原因 | ✅ 主方法 | 診斷「為什麼不用」需要探測動機、認知與過往經驗；搭配請受訪者當場打開自訂報表頁面，可區分「不知道」vs「試過放棄」。 |
| **量化數據前置分析（funnel / 事件追蹤）** | 低使用率的「在哪裡流失」 | ✅ 前置輸入 | 訪談前先請 data-analyst 拉：進入頁面率、建立報表完成率、重複使用率，用來校準招募分層與訪談探測點（上游銜接）。 |
| Diary study（一週日誌） | G1 流程的跨日節奏 | ⚠️ 備選 | 若週報流程橫跨多天（週一收數、週五交付），脈絡訪查單次到場拍不到全貌時加開；成本高，預設不啟動。 |
| 問卷調查 | 原因分布的量化驗證 | ❌ 本階段不採 | 還不知道「不用的原因選項」有哪些，先問卷會把假設塞給受訪者。質性研究結束後可作為後續驗證手段。 |
| 可用性測試 | 自訂報表的操作障礙 | ❌ 移交 | 若訪談發現主因是「不會用／設不出來」，後續交給 `usability-tester` 做完整任務式測試，本研究不重做。 |

### 3.2 場次設計（每位受訪者一場，二合一）

每場 **90 分鐘**，同一受訪者依序進行：

1. **Part A｜脈絡訪查（45-50 分）**：約在受訪者「實際要做週報」的時段，請他照平常方式做，研究員在旁觀察 + Master/Apprentice 式提問。記錄：資料來源、工具切換、複製貼上、手動計算、檢查行為。
2. **Part B｜深度訪談（30-35 分）**：聚焦自訂報表——認知、嘗試經驗、放棄點；最後請受訪者當場打開自訂報表功能走一次（非正式可用性觀察，僅作探測素材）。

> 排程約不到「正在做週報」時段者，Part A 改為「重演上一次週報」（請對方打開上週的檔案與信件，一步步重走），並於記錄中標註為 retrospective walkthrough（信心略低）。

## 4. 招募標準

- **必要條件**：
  - 其公司為本產品付費客戶，本人為後台活躍使用者（近 30 天有登入）
  - 每週（或固定週期）有產出營運報表的職責
- **分層（依量化前置分析校準）**：
  - **Segment A — 從未用過自訂報表**（事件紀錄為 0）：4-5 人
  - **Segment B — 試過但流失**（建立過 ≥1 張，近 60 天未再使用）：3-4 人
  - **Segment C — 持續使用者**：1-2 人（對照組，理解「什麼條件下會用」）
- **排除條件**：
  - 本公司員工、合作代理商員工、研究團隊朋友圈
  - 僅閱讀報表、不負責產出的角色（如只收信的主管）——但可列為後續研究對象
- **目標人數**：8-10 人（含對照組）
- **反偏誤提醒**：勿只招「願意回客服信的熱心客戶」；請 CSM 名單與 in-app 邀請各佔一半來源。

## 5. 時程

| 週次 | 工作 |
|------|------|
| W1 | 量化前置分析（data-analyst）＋ 招募啟動、訪談大綱定稿、pilot 1 場 |
| W2-W3 | 執行 8-10 場（每週 4-5 場，配合受訪者週報時段） |
| W4 | Affinity mapping、insight card 合成、journey map（每週報表流程） |
| W5 初 | 研究報告 + HMW 交棒（product-strategist / interaction-designer / usability-tester） |

## 6. 產出物

1. **Insight cards**（每張 ≥2 位受訪者證據，標註信心水準）
2. **Journey map**：「每週營運報表」流程（階段 × 動作 × 情緒 × 痛點 × 機會）
3. **低使用率原因框架**：認知／能力／信任／適配四象限歸因，各附證據
4. **HMW 清單**：交棒下游
5. （若樣本中浮現明顯角色分化）**Persona 草稿**：報表產出者 vs 報表消費者

## 7. 倫理與同意

- 訪談前說明研究目的、取得**錄音／螢幕錄影同意書**，受訪者可隨時中止
- 脈絡訪查涉及客戶營運數據：螢幕錄影前確認可遮蔽敏感欄位；報告中數據一律去識別化
- 報告以 P1-P10 代號呈現，不出現姓名、公司名與可回溯個資
- 報告須揭露樣本限制（如 retrospective walkthrough 場次數、招募來源偏向）與各 insight 信心水準

## 8. 上下游銜接

- **上游**：`data-analyst` 提供自訂報表 funnel 與使用分布（W1 前置）；`requirement-analyst` 提供功能原始需求文件（比對「設計意圖 vs 實際 workflow」落差）
- **下游**：
  - 原因歸因 + HMW → `product-strategist`（決定修功能 vs 改定位 vs 補 onboarding）
  - Journey map → `interaction-designer`（重新設計報表 flow）
  - 若主因為操作障礙 → `usability-tester`（任務式可用性測試）

## 9. 風險與備案

| 風險 | 備案 |
|------|------|
| 約不到「正在做週報」的時段 | 改 retrospective walkthrough，並標註信心水準 |
| Segment B（試過流失）名單太少 | 放寬至「建立過報表草稿未發布」者 |
| 週報流程橫跨多天，單場拍不全 | 對 2-3 位加開一週 diary study（每日 5 分鐘語音／截圖回報） |
| 客戶數據敏感無法錄影 | 改為研究員現場手繪流程圖 + 受訪者口頭確認 |
